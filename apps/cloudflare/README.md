# Cloudflare Factory Worker

This composition binds one SQLite-backed `FactoryObject`, one SQLite-backed `ManagedWorkObject` per stable thread identity, and a separate SQLite-backed `PrivateAssistantObject` for the owner-private Pi Durable conversation. `FactoryObject` runs the portable Core on `state.storage.transactionSync()`, persists Factory inputs/effects/events, routes a managed input to the thread Durable Object, and schedules recovery with alarms. `ManagedWorkObject` opens the same Pi Durable facade using that object's persistent storage and schedules Pi wake/recovery alarms. `PrivateAssistantObject` has its own SQLite Pi Durable/admission store and recovery alarm; its history is not part of a work-thread checkpoint. The Worker router does not contain a public remote-job injection route.

## Configure a protected deployment

`wrangler.toml` sets `workers_dev = false`, declares the Durable Object classes/migration, and selects Pi AI's real `openai` / `gpt-4o-mini` model. Use a custom operator-owned route and protect human Factory traffic with Cloudflare Access or a private gateway. A Tailscale client does not make a public Worker endpoint private. Keep owner sign-in, model, assistant, and execution-node credentials distinct.

From this directory, stage secrets without printing them (deployment is a separate operator action):

```sh
wrangler versions secret put UZINA_OWNER_TOKEN
wrangler versions secret put UZINA_PROVIDER_CREDENTIALS
```

`UZINA_OWNER_TOKEN` is a private random token of at least 32 non-whitespace characters (generate locally with `openssl rand -hex 32`). The Factory initializes its owner from this secret, storing only a hash in SQLite. Open `https://<protected-origin>/login?token=<token>` and confirm sign-in; there is no bootstrap request or UI token field. Keep this link private. Cookie sessions, single-use scoped invitations, and `/sharing` use the same portable handler as the native host. Revocation is checked on every request; a revoked configured token is not re-enabled after eviction.

`UZINA_PROVIDER_CREDENTIALS` is a Pi-style provider map, with only credentials this Worker needs. For example (dummy values):

```json
{
  "openai": { "type": "api_key", "key": "replace-me" },
  "anthropic": { "type": "api_key", "key": "replace-me" }
}
```

Use a **secret**, never a public Wrangler `vars` entry: [Worker secrets are encrypted text bindings](https://developers.cloudflare.com/workers/configuration/secrets/). No application encryption key or custom credential-ID indirection is needed. The Worker receives plaintext credentials only at runtime in memory. OpenAI, Anthropic, and Google API-key profiles are supported; choose the provider/model with non-secret `UZINA_MODEL_PROVIDER` / `UZINA_MODEL_ID` variables. Without selection, a stored OpenAI `gpt-4o-mini` is preferred, then an available model. Existing `UZINA_MODEL_API_KEY` + explicit provider/model deployments remain supported for compatibility.

For local workerd development, use `.dev.vars` (Git-ignored); these local files are plaintext and must remain private. OAuth login/refresh and machine filesystem/environment discovery remain unsupported on Workers. Local Bun instead reuses Pi's complete native resolver, including existing API-key/OAuth sign-ins and custom model configuration.

`bun run build:cloudflare` creates `build/index.js` with the pinned Worker-only Pi AI compatibility plugin and then invokes Wrangler's dry-run build. The same `build/index.js` artifact is used by Miniflare/workerd integration tests. The build checks Pi AI's exact `1.4.0` package version and expected auth-module exports, and fails if a required replacement seam is missing. The shims cover host-auth context, OAuth loaders, and Anthropic's native environment-helper imports. Use `wrangler deploy --dry-run --config wrangler.toml` to inspect the actual class bindings; a dry run does not deploy, create a production namespace, set secrets, configure Access, or prove cloud operation.

## Private routes and node setup

`workers_dev = false`; this repository defines no Worker route and does not configure Cloudflare Access. An operator must select a protected custom route/gateway before deployment and verify the actual ingress policy. Do not infer that a Worker URL is tailnet-private or claim that Access is configured. The daemon Factory binds only to loopback; Workers use the externally selected protected route.

## Owner-private Factory assistant

The owner provisions a named assistant credential through the existing Core owner operation and selects explicit factory-wide or narrower project/thread grants. The host never provisions a token or broadens grants. Keep the returned bearer only in `UZINA_PRIVATE_ASSISTANT_BEARER`; configure the matching non-secret `credentialId`, immutable `assistantId`, and accountable `ownerId` in the protected Worker configuration. Use `wrangler versions secret put` for `UZINA_PRIVATE_ASSISTANT_BEARER`, `UZINA_PRIVATE_ASSISTANT_CREDENTIAL_ID`, `UZINA_PRIVATE_ASSISTANT_ASSISTANT_ID`, and `UZINA_PRIVATE_ASSISTANT_OWNER_ID`; deploy that version separately. Use dummy values only in local workerd tests. This is independent of owner/browser, node, and model API credentials.

The dedicated Durable Object validates that exact identity through the ordinary authenticated Factory HTTP handler using `FactoryClient.me()`. Its custom `factory_*` tools are installed only in the private root; work-thread registries retain their existing remote execution tools and never receive this bearer. The assistant has no native filesystem/argv tools. Tool requests authenticate through Core each time, so current grant changes and revocation apply to subsequent calls. A missing, revoked, mismatched, or temporarily uncheckable assistant credential parks the assistant without affecting unrelated Factory work. The owner can still inspect the existing private history/status/receipts after assistant revocation. The owner-only routes are `/v1/private-assistant/status`, `/context`, `/receipts/:inputId`, and `POST /inputs` with stable `{ inputId, text }`; changed text for a reused ID conflicts.

The runtime pins its persisted assistant identity. Changing bearer identity does not adopt the old transcript; credential rotation/adoption, transcript export/deletion, and automatic token provisioning are unsupported. Preserve the private store and configure a newly reviewed runtime if identity replacement is needed. The `PrivateAssistantObject` class is additive SQLite migration `v2`; dry-run builds do not deploy the class, set Worker secrets, or configure Access.

The Worker applies Factory bearer credentials to owner operations/context/events/status. Connected execution daemons use separately provisioned node bearer credentials and initiate outbound registration, heartbeat, claim, and report requests. If Cloudflare Access is fronting the Worker, its policy must allow those node protocol paths without a human Access cookie (for example via a narrowly scoped bypass) while keeping them protected by the route's node credential and rate limits. The node credential is not an owner or model API key. No HTTP path accepts caller-selected execution jobs.

Owner workflow: open the protected owner sign-in link, provision node identities, provision mapped workspaces, and create threads with an explicit target. Submit input only to the assigned thread. `GET /v1/commands/:requestId`, `/v1/events`, and authorized `/context` and `/status` routes surface receipts and canonical model state.

`POST /v1/mcp` uses the same `FactoryObject` and Core operations as REST. It is the official SDK 1.32.2 Web Standard stateless Streamable HTTP/JSON profile with `Authorization: Bearer <active Factory credential>` on every POST. The stateless server stores no MCP session/auth snapshot; revocation/grant changes apply on subsequent requests. Query-string tokens and cross-origin `Origin` values are rejected; there are no wildcard CORS headers. Tokens are isolated by the single Factory Durable Object credential store and rejected by another Factory. See `packages/core/README.md` for the complete tool list, resource profile, and unsupported lifecycle operations. No execution-node or model-provider request receives this caller credential.

## Workspace-only checkpoint storage

`wrangler.toml` declares the `CHECKPOINTS` R2 binding with the operator-owned bucket name `uzina-workspace-checkpoints`; a dry-run does not create that bucket. The Factory DO constructs one capture-scoped streaming storage adapter. Missing storage fails closed. After an authenticated held source fence, an owner can admit `POST /v1/workspace-snapshots`, inspect its stable receipt, and retrieve only published references through the owner-authenticated blob route. The registered source node performs Git/filesystem capture and has capture-bound upload authority only; it cannot download arbitrary bucket hashes or access controller-private Pi artifacts.

The Worker verifies bounded metadata and streamed object digests before accepting `workspace-checkpoint-available`. It neither runs Git nor buffers an entire workspace. Full Git/workspace equivalence is checked during local inactive restore. Mandatory path exclusions and declared scope use the same non-backtracking matcher as the exporter, with an aggregate publication work limit. Rejected uploads can remain in private staging, and selected files or Git history may contain secrets; this is not a secret scanner or OS sandbox.

## Coherent managed-work checkpoint assembly

When the Worker has its `CHECKPOINTS` R2 binding, an owner may request `POST /v1/threads/:threadId/managed-work-checkpoints` with `{ contractVersion: 1, requestId, captureRequestId, workspaceSnapshotRequestId }`. This admission is accepted only for the exact owner, thread target/generation, still-held source fence, and available verified workspace snapshot; the initial status is `assembling` / `admitted`, not an availability claim. Deployments without the Worker assembly/storage adapters fail with `503 managed_work_checkpoint_assembly_unavailable` before creating an admission receipt. The local Bun Factory does not claim this Worker R2 assembly capability.

The Factory DO then exports the selected managed Pi root from the exact held capture, creates bounded versioned provenance from sanitized settled Factory command/effect metadata (identities, targets, generation, payload hashes, operations, terminal statuses, and timestamps), composes the existing v1 `quiescent-current-documents-no-forks-v1` bundle, persists immutable content-addressed private artifacts in a request-hashed namespace, and verifies the exact workspace/private object closure before atomically advancing status to `available`. When ordinary ManagedWork opens its runtime under the Core lifecycle permit, it records a bounded non-secret source profile in separate Durable Object metadata: the selected provider/model identifiers and the exact managed `remote_read_file`, `remote_write_file`, and `remote_run_command` v1 tool catalog. For an existing root, the model comes from its committed `pi.agent` document, not the host's creation default; changing that default does not reconfigure the root. The profile is not Pi logical session state, private-assistant state, or credential/configuration data. Cold raw export reads this recorded profile without resolving runtime options, constructing a Harness, contacting a provider, or reading status; it checks the model against the actual exported root document as well as the held capture, target, generation, and raw checkpoint checksum. Stale or unsupported model metadata does not advertise coherent compatibility. The full requirement list is persisted atomically with the runtime-export artifact stage and reused on later composition/recovery passes. A legacy source with no valid recorded profile refuses coherent assembly (status remains unavailable) while the raw managed-work export remains available; unknown custom registries are not advertised as compatible. Local destinations must explicitly support the exact `model:<provider>/<modelId>` and `tool:remote_*:v1` requirements in addition to the fixed v1 baseline; generic Pi compatibility alone is insufficient. Provenance deliberately omits original input/body/operation arguments, command outcomes, file/shell contents, execution reports/stdout/stderr and raw error diagnostics, session/auth/grant/credential data, provider configuration, and private-assistant history. For failed effects it retains only a bounded allowlist of normalized structured executor/controller error codes; successful effects keep `errorCode: null`, and unknown or inconsistent codes block publication. This metadata projection is bounded and complete; it rejects an oversized or unsettled set rather than truncating it. Core accepts publication only from a frozen result issued by the in-process closure verifier and bound to the exact persisted source/private object references and runtime requirements; copied or mutated summaries are not proof. A started export/write/compose effect with no durable output record is `uncertain`; reopening does not silently repeat it. A verified closure failure is blocked. The original workspace blobs remain in the workspace-only capture namespace; only the composed bundle's runtime, provenance attachment, inner manifest, and outer manifest enter the private request namespace. The same `CHECKPOINTS` bucket name does not make those authorization scopes interchangeable.

Owners read the durable receipt at `GET /v1/managed-work-checkpoints/:requestId` and retrieve one allowlisted binary object at `GET /v1/managed-work-checkpoints/:requestId/blobs/:sha256`. The route streams the binary body directly, requires the owner bearer, and exposes neither arbitrary R2 keys nor a JSON-bounded Factory RPC body. Workspace-only snapshot routes remain separate. On an owner-controlled local machine, use the returned manifest reference with the portable bundle validator/restorer; restoration ends at `prepared-inactive`. It does not run the managed Pi runtime, activate work, release the source fence, transfer ownership, or establish cloud-to-laptop continuity. Keep source-node workspace artifacts workspace-only; do not include Factory database copies, credentials, provider secrets, owner bearers, or private-assistant history.

### Owner-correlated source transfer hold

After an available coherent Checkpoint, the source Owner can reserve the already-held source capture with strict `POST /v1/threads/:threadId/managed-work-transfer-holds` body `{ contractVersion: 1, requestId, captureRequestId, checkpointRequestId }`. `GET /v1/managed-work-transfer-holds/:requestId` returns the immutable `held-awaiting-local-preparation` receipt to that current Owner, including the exact capture/control/fence, verified workspace snapshot, coherent manifest, actor, source binding, and original acceptance time. The stable request ID cannot be rebound. This receipt is last-committed evidence, not continuous physical or OS readiness.

The shared production route is available only when the Worker has both its existing `managedWork.exportCheckpoint` capability and `CHECKPOINTS` private storage binding. Without either, POST returns `503 managed_work_transfer_hold_unavailable` before writing a hold; status lookup does not depend on those current host capabilities. The hold reserves its capture, snapshot, and coherent Checkpoint against workspace relocation in either admission order, including blocked and uncertain relocation records. It prevents both existing Core capture-cleanup paths from deleting the held capture. The existing source fence, capture admission lock and ManagedWork runtime-permit path continue to block that selected source. This stage does not create local identity/readiness, retire the source, advance Ownership generation, commit ownership, release/expire/rebind the hold, or activate execution.

The end-to-end `authenticated cloud producer to standalone inactive consumer` test in `apps/daemon/test/standalone-factory.test.ts` exercises the production Cloudflare Durable Objects and Core HTTP routes under Miniflare/workerd, a real connected `ExecutionDaemon`/`ExecutionLoop`, and a separately bootstrapped local Owner/import host. It creates an actual source capture, verified workspace snapshot, available coherent Checkpoint, and durable hold. Concurrent hold admissions leave exactly one committed binding; discarded POST response bodies are recovered through owner status and exact retry, while changed request bindings and a competing relocation are refused. A second credential provisioned for the same immutable Owner retries the identical binding; revoking that credential blocks its next request without changing the binding visible to the still-valid Owner credential. Guest/viewer and node actors cannot admit or read a hold. This API has one immutable Owner actor, so it does not expose a second distinct Owner identity for an independent positive actor-conflict retry test. A full persisted Miniflare restart and reopening the daemon SQLite database retain the hold and native `source-capture-fenced` CONTROL; subsequent source input, public runtime reads, direct daemon writes, and cold ManagedWork input/context/resume paths remain blocked. A scheduled cold alarm does not invoke the runtime model, Owner blob/history reads remain available, and the distinct local import stays `prepared-inactive` while unrelated local Pi work remains usable. This proves those emulator paths only; the hold is not an OS readiness attestation and does not authorize local activation or source retirement.

### Workspace execution relocation and activation

The authenticated Worker/Core and connected `ExecutionLoop`/`ExecutionDaemon` consume the workspace relocation protocol after a held CONTROL, workspace snapshot, and coherent managed-work checkpoint. An owner starts the same prepared relocation with strict `{ contractVersion: 1 }` at `POST /v1/workspace-relocations/:requestId/activation-intent`; `GET /v1/workspace-relocations/:requestId` exposes its phase and evidence. The destination node claims only its own assignment at `POST /v1/nodes/:nodeId/workspace-relocation-activations/claim`, freshly verifies the original prepared tree and receipts, and reports readiness at `POST /v1/nodes/:nodeId/workspace-relocations/:relocationId/readiness`. After rechecking current owner/source/destination authorization, exact immutable checkpoint/snapshot/CONTROL/prepared bindings, held source fence, destination reservation, and absence of admitted work, Core transactionally retires the source, advances the destination epoch, changes the same thread's placement, and returns a durable exact activation command. The node applies that command without another restore and submits its correlated receipt to `POST /v1/nodes/:nodeId/workspace-relocations/:relocationId/activation-report`.

The activation status progresses through `intent` / `preflight-claimed`, `ownership-committed`, and `activated`, with `uncertain` as a parked fail-closed state. `prepared-inactive` remains preparation only, never an activation grant. Core keeps thread input/context/runtime/effect admission and the destination reservation closed from ownership commit until the exact authenticated destination receipt finalizes. A source epoch and destination's prior provisioned epoch are distinct: the new epoch is `max(sourceOwnershipGeneration, destinationOwnershipGeneration) + 1`; old CONTROL/snapshot/checkpoint/command/effect evidence retains its original epoch. New v1 preparation binds both epochs; persisted legacy v1 preparation without a destination epoch keeps its original binding and local-generation check rather than rewriting its digest.

Finalization never clears the source's durable CONTROL/local workspace fence, restores the source, provides rollback or timeout takeover, or transfers the managed Pi runtime. A later capture/move is a new authenticated operation with new capture/snapshot/checkpoint/relocation IDs, not a retry or replacement of the prior transfer. Historical status and allowlisted owner blob reads continue to use original immutable bindings but require current owner authorization/scope; a revoked credential has no historical access, and historical evidence cannot authorize new work or node reads. The existing cloud Pi thread/ManagedWork Durable Object/profile remains in place, and only after activation finalization can its next accepted input produce a workspace effect at the new target. Changes to a prepared tree across the readiness/commit await are refused and retained as uncertainty without overwrite; revocation blocks subsequent authenticated steps but cannot undo an already-consumed commit/effect.

The Miniflare/workerd + local R2 and real node-loop tests exercise a successful A0→B1→C2 sequence on the same cloud Pi context, separate destination epochs, unrelated X0 progress, and a distinct held-commit changed-tree/credential-revocation case that remains ownership-committed/barriered when the revoked node cannot report its local uncertainty. These are local emulator results only. They do not establish OS-level isolation, two-laptop/cloud-to-laptop operation, protected production ingress/secrets/R2, deployment, or managed-runtime/controller transfer.

## Workerd integration evidence

`bun test apps/cloudflare/test` exercises the production compatibility-built `cloudflare:workers` Durable Object classes under Miniflare/workerd, with SQLite storage, transaction receiver, RPC, alarms/eviction, and the root Worker route. Its composed test drives the real Pi AI OpenAI Responses provider using a bounded mocked outbound HTTP service and a dummy API-key value; the mock selects the remote tool and returns its final response without reaching the Internet or making a paid request. A separately authenticated local execution daemon performs the actual workspace effect. Provider auth-failure and compatibility-shim tests also run under the workerd-compatible build contract.

This emulator result is not a production Cloudflare deployment. Production credentials, custom route, Access configuration, a real remote API provider request, tailnet/client setup, and a second-laptop connection were not tested. A deterministic adapter is confined to test-support and is not a Workers fallback.
