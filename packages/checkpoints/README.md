# Workspace checkpoints (format version 1)

The base `captureWorkspaceCheckpoint` API captures and restores the **workspace** portion of a checkpoint; it does not infer managed state from a transcript or serialize Pi storage. Its opaque `runtimeArtifact` slot is versioned and integrity checked, and named attachments use the same content-addressed transport. The composed managed-work API below adds a separately validated public Pi logical profile.

## Public API

- `captureWorkspaceCheckpoint({ workspacePath, transport, includeGlobs?, excludeGlobs?, limits?, runtimeArtifact?, attachments? })` returns `{ manifest, manifestReference, manifestBytes }`; `manifestBytes` is the exact serialized byte sequence stored at the returned reference.
- `loadWorkspaceCheckpoint(manifestReference, transport)` loads and verifies the content-addressed JSON manifest.
- `validateWorkspaceCheckpoint(manifest, transport, options?)` validates format, compatibility, paths, bounds, and every referenced blob before a destination is considered.
- `previewWorkspaceCheckpoint(manifest, transport, options?)` returns the validation result and a summary containing selected file count/bytes, Git HEAD/branch, declared policy, omissions, and opaque artifact/attachment names. Pass `destinationPath` in preview options to include the empty-destination check.
- `restoreWorkspaceCheckpoint({ manifest, transport, destinationPath, ...options })` restores into a nonexistent or empty destination and returns the opaque runtime artifact and attachment bytes without activating anything or running commands.
- `BlobTransport` is the pluggable content-addressed interface (`putBlob`/`getBlob`). `FileBlobTransport` implements it in a local directory using SHA-256 filenames.

A blob transport must store immutable bytes under their lowercase SHA-256 digest and reject unavailable/corrupt objects. Cloud blob adapters should implement that interface and enforce their own request/response streaming limits. `FileBlobTransport` storage must be outside the captured workspace to avoid recursively capturing its own blobs. The manifest is itself stored as a blob; consumers persist its returned `manifestReference`.

For a runtime artifact, the destination must explicitly provide `supportedRuntimeFormats` and every supported `supportedRuntimeRequirements` string. This package does not treat an arbitrary artifact or transcript as executable/runtime state.

## Coherent managed-work bundle

`captureManagedWorkBundle({ managedWork, workspacePath, transport, attachments?, compatibilityRequirements?, limits? })` validates and prepares the public Pi logical checkpoint and requirements before Node workspace capture, then delegates final composition to the shared module-level `composeManagedWorkBundleFromWorkspace` seam. The seam accepts a workspace-only manifest, its exact stored bytes and content reference, and bounded Pi/attachment artifacts; it has no filesystem path, Node/Git dependency, or workspace-blob reads. The composition caller must already have verified workspace blob integrity externally. The seam verifies that the supplied manifest object matches the bounded source bytes/reference and validates workspace-only metadata, but does not redo Git validation or re-hash large workspace objects. It reuses their references in place and writes only the Pi artifact, named attachments, composed workspace manifest and outer manifest. The Cloudflare Factory controller consumes this seam only after its persisted capture and workspace-snapshot authorities are rechecked; it stores the private closure in a distinct request-hashed R2 namespace and runs `verifyManagedWorkCheckpointClosure` before publishing availability.

The result is a content-addressed outer manifest using `uzina-coherent-managed-work-checkpoint` version 1. It preserves the `quiescent-current-documents-no-forks-v1` profile, complete workspace metadata (Git bundle, staged index patch, selected files/binaries, omissions and integrity references), stores the Pi checkpoint as the versioned runtime artifact, and stores named opaque attachments such as Factory command/effect provenance. The Factory provenance attachment is a bounded metadata-only projection of persisted settled receipts (identities, target/generation, payload hashes, operations, terminal statuses, timestamps, and allowlisted normalized structured codes for failed effects); it excludes original inputs/arguments, outcomes, reports, contents, raw error diagnostics, credentials, and configuration rather than truncating selected evidence. `validateManagedWorkBundle(reference, transport, { supportedRuntimeRequirements })` verifies the outer checksum, every resource/hash/path, compatibility, Pi checkpoint checksum/graph/profile, and requirements before restore. The fixed v1 baseline includes the managed-work profile and `pi-durable:1.4.0`; source producers must additionally record the selected `model:<provider>/<modelId>` and each installed `tool:<name>:v1` requirement, which destinations must explicitly support. The Cloudflare ManagedWork adapter derives the model from the existing root's committed `pi.agent` document (using the creation default only for a new root), checks the static model catalog actually opened under the Core permit, and adds its installed managed remote-tool catalog. It persists the non-secret profile outside Pi logical/private-assistant storage and binds its exact requirements to the recorded runtime artifact stage. Raw export reads this persisted profile without resolving runtime options and verifies its model against the exported root document; stale metadata cannot substitute a changed host default for the root's selection. A missing or unsupported legacy source profile refuses coherent Worker assembly; it does not make a generic baseline bundle truthful for that source. Direct composition callers remain responsible for supplying their source requirements.

`restoreManagedWorkBundle({ manifestReference, transport, destinationPath, supportedRuntimeRequirements, openStorage })` accepts only a missing or empty inactive destination. It stages the workspace and a fresh raw Pi storage under a sibling temporary root, imports logical Pi records without constructing a Harness, writes attachments and a stable `prepared-inactive` receipt, then places the complete root with one directory rename. The prepared root contains `workspace/`, `managed-work.sqlite`, `.uzina/attachments/`, and `.uzina/prepared-restore.json`. Repeating the same bundle restore first revalidates the prepared workspace files/modes/Git index, logical Pi storage records, attachments, and current compatibility requirements; an unchanged destination returns the same receipt without importing again, while changed data fails closed. It never calls a model/tool or starts a scheduler. Callers must explicitly activate only after separate authorization; the receipt is preparation evidence, not ownership transfer.

The local `FileBlobTransport` remains the supported offline file transport. `R2BlobTransport` is a small structural adapter for R2-compatible `put/get` APIs; it writes by SHA-256 name with an `If-None-Match: *` precondition, verifies duplicate content, and checks every read. The Cloudflare Factory has a production-consumed Worker assembly path backed by its configured `CHECKPOINTS` bucket, request-private storage quotas, durable effect stages, and an owner-only streaming allowlist. Bun Factory deployments do not have this private Worker adapter and reject coherent-checkpoint admission before persisting it. The Miniflare workerd vertical exercises the real fenced source capture, workspace snapshot, controller composition, closure verification, owner retrieval, and local `prepared-inactive` restoration. This does not implement destination activation, source-fence release, ownership transfer, Cloudflare production deployment, or two-machine continuity.

## Captured filesystem and Git shape

The workspace root must be the root of a non-shallow, non-empty Git checkout. Regular working files, selected untracked files, internal relative symlinks, binary bytes, and the executable bit are represented as logical relative-path entries. File permission bits other than executable are not preserved. Paths are portable UTF-8 relative paths; absolute paths, `.git`, traversal, Windows-reserved names, alternate separators, non-UTF-8 names, and symlinks escaping the root or traversing another captured symlink are rejected. Nested repositories, submodules, unresolved merge conflicts, sparse/split indexes, intent-to-add, assume-unchanged, and skip-worktree index states are refused.

A Git bundle stores commits/history reachable from all Git refs plus the current HEAD; a binary staged patch stores selected index changes relative to HEAD. Restoring applies that patch to the index, then materializes the selected working tree. This preserves ordinary staged and unstaged differences, staged deletions/additions, and selected untracked files. The restore is a normal inactive checkout, not a linked-worktree registration; source worktree administrative files, absolute worktree paths, remotes, reflogs, Git configuration, hooks, and machine-local Git state are not copied. Bundle restoration uses argv-based Git commands with system/global config disabled, an empty hook template, and no shell interpolation.

The manifest declares `includeGlobs` (null means all paths) and `excludeGlobs`; default exclusions omit `.env`/`.env.*`, credential/auth filenames, `.pi/agent/**`, `.ssh/**`, and `node_modules/**`. Each excluded, out-of-scope, or over-file-limit path is reported in `workspace.omissions`. Glob syntax supports `*`, `?`, and `**` over slash-separated relative paths. The Node exporter and portable publication validator share a deterministic non-backtracking matcher. Portable publication accounts for each policy pattern code unit once, then each NFA state activation or examination against selected workspace entries and staged-path declarations; a combined 64,000,000-unit budget is enforced for one manifest. Exceeding the budget rejects validation rather than allowing unbounded synchronous policy work. The matcher reuses fixed bounded state arrays, and directory pruning remains conservative when includes contain wildcard segments; traversal is also bounded by the path limit. The workspace is never swept beyond its selected checkout. Still, **arbitrary selected files and attachments may contain secrets**. In addition, preserving Git history necessarily preserves content reachable through its refs, including old committed content: this format cannot both retain those refs/history and redact secrets previously committed there. Inspect scope and history before publishing a bundle.

Hard bounds are 100,000 workspace files, 200,000 traversed paths, 10,000 omission records, 64 MiB per workspace file, 32 MiB per runtime artifact or attachment, 512 MiB total checkpoint data, and 16 MiB serialized manifest. Callers may lower but not raise capture limits. A selected file exceeding its per-file bound is omitted and reported; aggregate/resource-count overflow refuses capture. Git bundle output and staged-patch output are stopped at their remaining checkpoint-size budget before the generated bytes are read or accumulated further.

Before destination effects, restore validates supported format/capabilities/Git/runtime requirements, bounds, duplicate/conflicting paths, traversal and symlink targets, every content hash/size, the Git HEAD and staged path set, and that the destination is nonexistent or empty. It prepares a sibling staging checkout and only then replaces the empty destination. A restore is left inactive; it neither grants placement authority nor starts a runtime. The higher-level authenticated Core/connected-daemon workspace relocation protocol can activate only the exact prepared receipt after source-fence, current-owner, destination, and fresh-tree checks; preparation alone remains insufficient. That protocol retains the source fence and relocates workspace execution authority without transferring the managed Pi runtime.
