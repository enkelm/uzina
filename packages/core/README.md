# Factory Core

`@uzina/core` provides owner-authenticated Factory operations over the portable `FactoryDatabase` interface. The local Bun SQLite and Cloudflare Durable Object adapters use the same service behavior.

## Separate durable queues

Factory managed-input intents remain in `dispatch_intents`; they contain `{ kind: "managed-input", text }` and are consumed only by `ManagedRuntimeDispatch` (`FactoryService.dispatchNext`). They are never returned to execution nodes.

Bounded remote effects live separately in `execution_jobs`. The trusted in-process bridge is `FactoryService.enqueueManagedRemoteExecution(threadId, piTaskId, piCallId, operation)`. It looks up the active accepted input and derives request ID, actor, node, workspace, and ownership generation from persisted Factory rows. The model supplies only the bounded operation arguments. There is no public or owner-facing job-injection route.

Each managed effect ID is deterministic from the accepted request and durable Pi conversation/task/tool-call evidence. Pi Durable records that evidence in the tool task memo before dispatch. Reusing a Pi call returns the existing remote receipt; reusing an effect ID for another payload or Pi evidence is a conflict. The Core receipt correlates remote effect receipts in optional `executionEffects`, and committed events correlate request ID, Pi task/call, job ID, destination, and generation.

`dispatchStatus: "dispatched"` means Pi Durable accepted the submission, not that its model run or workspace effect completed. Hosts settle command receipts only from Pi's durable submission record. Interrupted controller work is `uncertain`; a reported uncertain remote effect also fences its parent receipt as uncertain. A managed-tool wait timeout cancels a definitely unclaimed effect or fences a claimed effect from future node claims. One late report from the same persisted node assignment may reconcile the effect receipt, but it does not rewrite the already-uncertain parent Pi command. Duplicate dispatch or a later blind retry never completes these receipts.

## Workspace-scoped current ownership authority

Core stores the current ownership generation directly on each provisioned `workspaces` row, whose immutable `node_id` binds the authority to its node. New workspaces are provisioned at generation 0. The legacy `factory_meta.ownership_generation` value remains for old-data compatibility and is used only to backfill workspaces once when migrating a schema that predates the scoped column; it is not current placement authority afterward. Migration refuses contradictory thread or node-workspace observations and does not rewrite existing assignment or receipt evidence.

Current thread, input, effect, node-report, capture, and checkpoint gates compare a saved assignment with the exact provisioned workspace, node, and scoped generation. Generation values persisted on accepted inputs, effects, CONTROL, snapshots, checkpoints, and relocation records remain immutable evidence of their original assignment. A workspace epoch does not imply that a disconnected process has stopped.

The scoped-authority prerequisite itself does not advance generations, activate a prepared destination, change a thread target, unfence a source, or transfer managed runtime. The authenticated relocation pipeline below separately consumes a prepared receipt, commits one scoped destination epoch, and finalizes only on the exact destination receipt; historical bindings still do not grant current-work authority.

## Authenticated execution-node protocol

The owner provisions a node with `POST /v1/nodes` and creates each allowed workspace with `POST /v1/workspaces`. The one-time-visible node bearer credential is bound to the provisioned node actor. Node routes derive identity from that credential and match it to the path and schema body:

- `POST /v1/nodes/:nodeId/register`
- `POST /v1/nodes/:nodeId/heartbeat`
- `POST /v1/nodes/:nodeId/jobs/claim`
- `POST /v1/nodes/:nodeId/jobs/:jobId/report`

All four requests and responses use `@uzina/contracts/execution`. Registration persists the node's capability report and owner-permitted workspace/generation/state reports. Claims persist claim evidence and return the same assigned job on retry after a lost acknowledgement; reports are checked against the persisted assignment and payload digest and exact duplicates reconcile the original report. Neither lost acknowledgements nor controller/node reopen require an in-memory prior claim. Interrupted node effects remain uncertain and are not replayed.

Remote-effect admission validates the persisted node, active selected workspace, online heartbeat, that workspace's current scoped ownership generation, and capability. Effects use immutable stable IDs and payload hashes. A controller report stores its full correlated receipt and event. A failed model or unavailable destination does not create a remote job.

## Managed-work capture quiescence

The local host's `captureManagedWorkCheckpoint({ credential, threadId, transport })` first authenticates the supplied owner credential, then uses Core `beginManagedWorkCapture()` to acquire a durable thread/workspace admission fence and a trusted `workspaceCaptureQuiescence` adapter before reading Pi or the workspace. The local `ExecutionDaemon` adapter persists the same capture ID, rejects queued/running/uncertain local effects and blocking Rex processes, and blocks subsequent direct job/Rex admission. Core reuses its existing owner authorization checks. Capture refuses a workspace assigned to multiple threads and rejects queued, unavailable, running, dispatched, or uncertain managed inputs plus queued, claimed, or uncertain workspace effects. It does not pause unrelated work. While the fence exists, Core rejects new input/thread/effect admissions and prevents queued claims or unavailable-input requeue for the selected resources. The local host releases the fence after a known success/failure; a process crash leaves the durable lock in place.

An owner can inspect restart-surviving locks with `FactoryService.listManagedWorkCaptures(session)`. After verifying the node state, clear both durable halves using `ExecutionDaemon.endWorkspaceCapture(captureId)` and `FactoryService.endManagedWorkCapture(session, captureId)`; neither is auto-expired. The local host waits for in-flight captures before shutdown. The in-process provenance seam `getManagedWorkCaptureProvenance(session, threadId, captureId)` is available only under the active owner-authorized fence and returns the selected command/effect receipts for the bundle attachment. These are evidence, not imported users, credentials, permissions, or execution authority. Capture does not transfer ownership or fence a different machine.

The source requires a trusted local workspace-ID-to-directory mapping supplied as `workspaceDirectories` and an executor/Rex quiescence adapter supplied as `workspaceCaptureQuiescence` to `createStandaloneFactoryServer`; without either capture refuses. It also refuses two configured workspace IDs that resolve to the same local directory. The existing local snapshot helper remains an in-process API and releases its locks after a known capture settlement. It is not the remote-control lifecycle below.

### Remote source capture-control admission

Owner-authenticated `POST /v1/threads/:threadId/capture-controls` accepts a stable `{ contractVersion: 1, requestId }`; `GET /v1/capture-controls/:requestId` returns the same durable receipt after reopen. Core derives and stores the immutable actor, thread, node, workspace, generation, request/control/capture identities, and acquires the selected managed-work/workspace admission lock atomically before dispatch. Reusing a request ID for another thread/target conflicts. The durable `capture_control_requests` queue is separate from `dispatch_intents` and `execution_jobs`; only the provisioned node identity can claim and report its own control through `/v1/nodes/:nodeId/capture-controls/claim` and `/v1/nodes/:nodeId/capture-controls/:controlId/report`.

The connected node persists a correlated control receipt and local workspace fence in SQLite before it can report `source-capture-fenced`. It confirms quiescence using configured workspace root overlap checks, unsettled local execution receipts, and structured persisted Rex lifecycle records. A known active/uncertain writer returns a durable `blocked` refusal; unavailable nodes stay queued. Core admission remains fenced after `blocked`, lost acknowledgements, restart, or source-fence confirmation. There is no automatic release/unfence API in this phase. `source-capture-fenced` confirms only the Uzina-managed workspace admission fence: it is **not** a completed checkpoint, workspace snapshot, transferable bundle, ownership move, or proof that arbitrary unmanaged OS processes cannot write. Do not infer source fencing from node heartbeat or registration reports.

CONTROL itself performs no filesystem/Git capture, Pi export, R2/blob transfer, destination preparation/activation, or ownership transfer; the source does not execute a model or tool to establish its fence. The separate snapshot, coherent-checkpoint, and relocation protocols below may consume this same held fence.

### Coherent-checkpoint anchored relocation admission and preparation

Owner `POST /v1/threads/:threadId/workspace-relocations` accepts the strict body `{ contractVersion: 1, requestId, checkpointRequestId, destination: { nodeId, workspaceId } }`. The request ID is stable; Core derives the source capture, snapshot, workspace-manifest digest, thread/project, actor, and current generation only from that owner's already-published `available` coherent-checkpoint receipt. One checkpoint/source snapshot and one provisioned destination can be reserved once; retries retain the same relocation ID and conflicting bindings fail. Owner `GET /v1/workspace-relocations/:requestId` rechecks the original source fence and binding.

Core reserves the exact distinct, unassigned destination workspace in the admission transaction. New thread, managed-input, remote-effect, and capture admission for that workspace remains blocked; unrelated workspaces remain available. Offline destination nodes keep the request `queued` and are never replaced. An authenticated destination node claims only its own immutable assignment at `POST /v1/nodes/:nodeId/workspace-relocations/claim`; the assignment binds the original checkpoint, capture, snapshot, source and destination, generation, and verified workspace-manifest digest. The node-only `GET /v1/nodes/:nodeId/workspace-relocations/:relocationId/blobs/:sha256` streams only a hash/size-listed blob from the original workspace snapshot while the same destination claim and source fence remain valid. It does not grant source uploads, owner bearer access, or coherent Pi/provenance/private artifact reads. `POST /v1/nodes/:nodeId/workspace-relocations/:relocationId/report` accepts only the authenticated destination's exact assignment and a local receipt digest; this is node evidence, not independent filesystem verification by Core.

Core owns durable owner admission, destination reservations, claim/report authorization, and preparation evidence. The connected `ExecutionLoop` and `ExecutionDaemon` consume that assignment, stream and verify its workspace objects, and persist a local inactive receipt before reporting `prepared-inactive`. Core does not independently verify the destination filesystem; a later observed preparation verification failure can only degrade the prepared report to `uncertain`, bound to the previous receipt digest with the original evidence preserved. An activation-time tree change is a separate command-bound activation uncertainty, not a replacement preparation receipt. This preparation endpoint does not itself activate the destination, change the thread assignment or workspace ownership generation, release the source fence, establish two runnable copies, or transfer managed Pi runtime ownership. A preparation outcome comes from the authenticated destination consumer, not an owner-settable API.

### Authenticated workspace relocation activation

The owner may begin execution cutover only against that same `prepared-inactive` relocation ID with strict `{ "contractVersion": 1 }` at `POST /v1/workspace-relocations/:requestId/activation-intent`. Core derives all source, destination, epoch, manifest, and prepared-receipt bindings from the persisted relocation; the owner cannot choose an activation ID, target, generation, proof, or success outcome.

The authenticated destination calls `POST /v1/nodes/:nodeId/workspace-relocation-activations/claim`. Before Core has committed ownership it receives one durable preflight assignment bound to the original prepared receipt and source capture report. New preparation claims and reports also carry B's separately provisioned destination generation; legacy v1 records without that field keep their original binding and legacy local-generation check rather than being rewritten. B must freshly verify its real Git/index/files/cache and the existing restore verifier, then report the readiness receipt to `POST /v1/nodes/:nodeId/workspace-relocations/:relocationId/readiness`. Core rechecks the exact source CONTROL/checkpoint/snapshot binding, the owner credential, current source assignment, held Core lock, absence of active permits/input/effects, the exact destination reservation and its independent local generation, and safe generation arithmetic. In one SQLite transaction it retires A in Core, advances B to `max(sourceGeneration, destinationGeneration) + 1`, updates the same thread placement, and records the immutable activation command. The readiness response and repeated claim return that same command; neither retry creates another relocation or restore.

B applies that command locally without restoring again, then reports its correlated activation receipt to `POST /v1/nodes/:nodeId/workspace-relocations/:relocationId/activation-report`. Core finalizes only that authenticated exact receipt. Until finalization the existing thread lock and destination reservation block runtime, input, effects, and ordinary claims; uncertainty parks the transition. Successful finalization releases the pending Core thread-admission barrier/reservation and enables the same cloud runtime to use the persisted destination target. It never removes the source's original CONTROL request or node-local fence. Delayed old-source reports are recorded as fenced for that retired workspace without suppressing unrelated workspace reports from the same node; the destination's pre-activation old-epoch observation is transition-aware and never current execution authority.

Owner status and allowlisted CONTROL, snapshot, coherent-checkpoint, and relocation evidence remain readable only when the caller still has current owner authorization and scope; responses identify the original binding as `historical` / `historical-inactive`. Revoked credentials do not retain historical access. Historical evidence cannot authorize runtime, jobs, a new capture/relocation, or node reads. The connected daemon/`ExecutionLoop` consumes the claim, readiness and activation-report protocol, and a successfully finalized move lets the same cloud Pi thread continue at its new persisted workspace target. A later capture/move is a genuinely new operation with new request, CONTROL, snapshot, checkpoint, and relocation identities; it is not a retry or replacement for the completed historical move.

The source is retired in Core at ownership commit, and its original node-side CONTROL fence remains held permanently; activation finalization never unfences the source. The destination epoch is `max(sourceOwnershipGeneration, destinationOwnershipGeneration) + 1`, so immutable source/checkpoint evidence can retain its older epoch while the destination starts at its own provisioned epoch. New v1 preparation/readiness records bind the destination's separate prior epoch. Persisted legacy v1 records that lack this field retain their original binding and legacy local-generation check; migration does not rewrite historical digests.

The admission barrier remains in force through `ownership-committed` until Core receives the exact authenticated destination activation receipt. Before commit, a known refusal leaves the source/current target in place; after commit, an accepted uncertainty report leaves the new target and barrier in place without pretending the move completed or rolling back. If the destination credential is revoked before that report can be accepted, Core remains `ownership-committed` rather than claiming a report it did not receive. Credential revocation at an awaited phase denies subsequent authenticated operations but cannot undo bytes already consumed or an effect/transaction already underway. There is no timeout takeover, rollback, or source fallback. These local Bun/Miniflare/workerd/R2 proofs do not establish an OS sandbox, two-laptop operation, protected production ingress/secrets/R2, deployment, or managed-runtime/controller transfer.

## Authorized queries and MCP transport

Authenticated clients may query `GET /v1/threads/:threadId/context` for canonical Pi model context, `GET /v1/threads/:threadId/status` for Pi Durable inspection/status, and `GET /v1/commands/:requestId` for the durable input receipt and admitted effect receipts. `GET /v1/threads/:threadId/runs?limit=1..100` lists accepted input command receipts for that thread; the current application has no separate persisted Run resource. `GET /v1/threads/:threadId/lifecycle-capabilities` reports the supported lifecycle profile. `GET /v1/events` returns committed events in an authorized bounded cursor page.

`POST /v1/mcp` is a separately importable `@uzina/core/mcp` adapter built on the official `@modelcontextprotocol/sdk` `1.32.2` Web Standard Streamable HTTP transport. It uses stateless JSON responses: the SDK server/transport is created per HTTP request with session generation disabled. Each request must carry `Authorization: Bearer <active Factory credential>`; each request authenticates against the current Factory credential store, and Core rechecks active credentials and current grants for data and mutations. MCP `GET` SSE is not supported (authenticated requests receive `405 Allow: POST`). Query parameters, including `access_token`, are refused. There is no CORS response or wildcard origin; if `Origin` is present it must exactly match the request URL origin, and a mismatched `Host` is refused. The official SDK client has been tested through initialize, tool listing, and tool calls.

The MCP tools are `list_projects`, `list_threads`, `list_runs`, `get_receipt`, `get_context`, `get_status`, `list_nodes`, `list_workspaces`, `submit_input`, `get_events`, `get_lifecycle_capabilities`, and `request_lifecycle_operation`. Each work target is an explicit project/thread/request ID. Lists/events have a maximum page size of 100; serialized tool results are limited to 256 KiB. `submit_input` requires a stable application `requestId`, independent of MCP JSON-RPC correlation IDs, so lost acknowledgements reconcile with `get_receipt` or a repeated identical call. `stop`, `native-cli`, and `transfer` are explicitly refused before effects; no corresponding operation is simulated.

The token's resource audience is the single Factory represented by the authenticated Core database: token hashes are looked up only there, so a credential issued by one Factory is rejected by another. The endpoint additionally checks exact request Host/Origin binding. This is not an OAuth/resource-indicator issuer and does not make deployment ingress private; a Worker route or Access policy is not configured by this package. MCP never forwards the caller's credential to an execution node or model provider.

## Owner-administered assistant access

Assistant credentials are normal authenticated Core actors with an immutable assistant ID and accountable `ownerId`; that attribution does not grant human owner administration. `POST /v1/credentials` may specify `assistantGrants` as exactly one `{ "type": "factory" }` grant or a strict set of existing project/thread grants. Thread grants to owner-private threads are rejected. `PUT /v1/credentials/:credentialId/grants` replaces the stored scope and increments its access generation; only the human owner may provision, change, or revoke assistant grant authority. Revoke or replace the credential when removing its authority. Human browser credentials are not used in assistant tools.

For backwards compatibility, owner-provisioned assistant credentials created through the legacy request with no `assistantGrants` receive an explicit persisted factory-wide grant. Database initialization migrates pre-existing grantless assistant credentials to that same explicit row; there is no implicit assistant `isOwner` bypass. Scoped assistant grants apply through the same `FactoryAccessPolicy` for REST and MCP and are rechecked before dispatching queued input and authorizing new remote effects. A factory-wide assistant retains the previous access to owner-private context; human Guests/Viewers cannot access owner-private threads. Grant scope is not an OS sandbox, and revocation cannot undo external effects already admitted or dispatched.

## Persistent owner-private Factory assistant ingress

`GET /v1/me` now additively returns the active non-secret `credentialId` alongside the actor and participant. `FactoryClient.me()` runtime-decodes that identity; a host can require the configured assistant credential, immutable assistant ID, and accountable owner ID to match before opening/resuming tool-capable tasks. This endpoint does not disclose a bearer or cache grants.

Standalone Bun exposes owner-only `GET /v1/private-assistant/status`, `GET /v1/private-assistant/context`, `GET /v1/private-assistant/receipts/:inputId`, and `POST /v1/private-assistant/inputs` (`{ inputId, text }`). Cloudflare exposes the same routes through its Worker router. Both authenticate a human owner through Core; role is never supplied by the client. These inputs are admission metadata correlated to a Pi Durable submission in a separate private storage unit, not rows in `threads`, `dispatch_intents`, or `command_receipts`. Guest, Viewer, node, and assistant credentials are denied access. An unavailable/revoked assistant credential parks new inputs/resume/tool calls without preventing an owner from reading existing history and receipts.

## Production seams and limits

- `FactoryService.registerExecutionNode`, `heartbeatExecutionNode`, `claimExecutionJob`, and `reportExecutionJob` implement the node-facing Core operations.
- `FactoryService.enqueueRemoteExecution` / `getRemoteExecutionReceipt` are trusted in-process bridge seams; they must not be exposed as an anonymous or owner-facing job injection API.
- `enqueueManagedRemoteExecution` is the managed-Pi bridge and does not accept actor, node, workspace, or generation supplied by the model.
- `@uzina/contracts/execution` remains the wire contract. Optional command `cwd` is interpreted as a relative path within the selected workspace; the daemon rejects traversal, absolute paths, missing/non-directory paths, and symlink escapes.
- `FactoryObject` runs Core over `state.storage.transactionSync`; the actual workerd class binding and local SQLite adapter are both covered by composed tests.
- This slice proves a local standalone execution path and a Miniflare/workerd composition. It does not claim a production Cloudflare deployment, Tailscale ingress configuration, or a second-laptop operation. Arbitrary external writes and commands cannot be made exactly-once; uncertain receipts require reconciliation.
